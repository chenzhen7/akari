# Akari 架构对比与优化建议

> 生成时间：2026-07-13
>
> 研究方法：在 GitHub 上选取 3 个技术栈最贴近的优秀开源项目，阅读其核心源码，并与当前 `akari` 项目做架构与代码层面的对比分析。

---

## 一、对比项目

| 项目 | GitHub | 核心定位 | 与 Akari 最相关的亮点 |
|---|---|---|---|
| **CLITrigger** | [HyperAITeam/CLITrigger](https://github.com/HyperAITeam/CLITrigger) | Node + Express + SQLite + WebSocket + React/Vite + node-pty + simple-git，多 Agent 并行 dashboard | 后端分层、二进制 WebSocket 帧、CLI Adapter 抽象、终端持久化、崩溃恢复 |
| **Constellagent** | [owengretzinger/constellagent](https://github.com/owengretzinger/constellagent) | Electron + React + node-pty + Monaco，多 Agent 桌面端 | 终端状态恢复（snapshot + replay）、IPC API 结构化、Cron 自动化、PR 集成 |
| **agent-worktree** | [nekocode/agent-worktree](https://github.com/nekocode/agent-worktree) | Rust CLI，专门做 AI agent 的 git worktree 工作流 | 原子 merge/dry-run、退出码契约、copy_files 沙箱、shell wrapper 设计 |

---

## 二、架构层面的核心优化建议

### 1. 后端路由与分层：把 `index.ts` 拆成 Fastify 插件

**现状问题**：`apps/server/src/index.ts` 约 682 行，路由注册、WebSocket 处理、业务编排混在一起。

**CLITrigger 的做法**：Express 也按领域拆成 `routes/sessions.ts`、`routes/execution.ts`、`routes/projects.ts` 等 20+ 路由文件，service 层独立。

**优化方向**：

```text
apps/server/src/
├── plugins/
│   ├── websocket.ts          # WebSocket 注册与客户端管理
│   └── static.ts             # SPA fallback / 静态资源
├── routes/
│   ├── sessions.ts           # /sessions 相关
│   ├── git.ts                # /repo/* 与 /sessions/:id/git/*
│   ├── files.ts              # 文件浏览/编辑
│   ├── workspace.ts          # /workspaces
│   ├── tabs.ts               # tab 管理
│   └── canvas.ts             # canvas edges
├── services/
│   ├── session-lifecycle.ts  # 创建/删除/归档
│   ├── tab-service.ts        # tab CRUD
│   ├── diff-service.ts       # diff 计算与广播
│   └── terminal-coordinator.ts # 终端创建/resize/回放
└── index.ts                  # 只负责组装
```

每个路由文件用 `fastify.register(async function (fastify) { ... })`，共享 `SessionManager` 等依赖通过 `fastify.decorate`。

---

### 2. 数据访问层：从手写 SQL 抽离 Repository

**现状问题**：SQL 直接散落在 `SessionManager`、`WorkspaceManager` 里，schema 变更成本高。

**CLITrigger 的做法**：`db/queries.ts` 集中所有手写 SQL CRUD，`db/schema.ts` 管理迁移。

**优化方向**：

- 新增 `apps/server/src/db/repositories/`：
  - `session.repository.ts`
  - `workspace.repository.ts`
  - `settings.repository.ts`
  - `canvas-edge.repository.ts`
- `SessionManager` 只调用 repository，不直接写 SQL。
- 引入轻量迁移框架：Drizzle ORM 或 Kysely。SQLite 场景下 Drizzle 体积小、类型安全，且迁移文件可版本化。

---

### 3. WebSocket：从全量 JSON 广播改为按 session 订阅 + 二进制帧

**现状问题**：当前所有客户端接收所有会话数据，高频终端输出时 JSON 序列化开销大。

**CLITrigger 的做法**：
- 前端显式 `subscribe(sessionId)` 后才接收该 session 数据。
- 终端输出用自定义二进制帧 `[kind(1B) | sessionIdLen(1B) | sessionId | payload]`，比 JSON 减少约 33% 体积。
- `bufferedAmount > 4MB` 时自动退订后台标签页。

**优化方向**：

```typescript
// apps/server/src/websocket/broadcaster.ts
interface Client {
  socket: WebSocket;
  subscribedSessions: Set<string>;
}

function broadcastBinary(sessionId: string, data: Buffer) {
  for (const client of clients) {
    if (!client.subscribedSessions.has(sessionId)) continue;
    if (client.socket.bufferedAmount > 4 * 1024 * 1024) {
      client.subscribedSessions.delete(sessionId); // 背压保护
      continue;
    }
    client.socket.send(encodeTerminalFrame(sessionId, data));
  }
}
```

终端数据走二进制，状态事件仍走 JSON，两者职责分离。

---

### 4. 终端持久化：从内存 ring buffer 升级为持久化回放

**现状问题**：`TerminalMultiplexer` 只保留 5000 条内存缓冲，页面刷新后丢失。

**Constellagent 的做法**：
- 主进程维护 `outputSeq` 和 `replayChunks`（默认 8M 字符）。
- `sessionStorage` 保存终端快照 + 序列号。
- 渲染进程重载后调用 `pty.reattach(ptyId, sinceSeq)` 补齐缺失输出。

**优化方向**：

```typescript
// apps/server/src/terminal-mux.ts
interface TerminalInstance {
  pty: IPty;
  outputSeq: number;
  replayBuffer: RingBuffer<{ seq: number; data: string }>;
}

// 新增 terminal-buffer.repository.ts，按 (sessionId, terminalId, seq) 滚动持久化
const MAX_RETAINED_BYTES = 2 * 1024 * 1024;
```

这样刷新页面后可重连并恢复历史输出。

---

### 5. Worktree 管理：引入 dry-run 与原子 merge

**现状问题**：`worktree-manager.ts` 的 `mergeIntoCurrentBranch` 直接执行 merge，冲突时残留半成品状态。

**agent-worktree 的做法**：
- merge 前先 `dry_run_merge`（squash 用 `--squash --no-commit`，merge 用 `--no-ff --no-commit`）。
- 冲突则清理并 checkout 回原分支。
- 失败一律 rollback HEAD + reset_merge，worktree 保留现场。

**优化方向**：

```typescript
// apps/server/src/services/merge-service.ts
export async function mergeBranchAtomic(opts: {
  repoPath: string;
  sourceBranch: string;
  targetBranch: string;
  strategy: 'squash' | 'merge';
}): Promise<{ success: true } | { success: false; reason: 'conflict' | 'dirty' | string }> {
  const originalBranch = await gitService.getCurrentBranch(repoPath);
  // 1. checkout target
  // 2. dry-run merge --no-commit
  // 3. 冲突 -> cleanup, checkout original, return conflict
  // 4. 真实 merge -> 失败 -> reset, checkout original
  // 5. 成功 -> post_merge hook
}
```

这对“夜间 Agent 自动 merge”场景尤其重要。

---

### 6. Agent 适配器：扩展 Adapter 接口，统一处理 CLI 差异

**现状问题**：`AgentAdapter` 只生成 `PtyCommand[]`，不同 CLI 的就绪检测、stdin 提交序列、信任对话框等逻辑分散。

**CLITrigger 的做法**：

```typescript
interface CliAdapter {
  command: string;
  displayName: string;
  buildArgs(opts: unknown): string[];
  needsStdin(mode: string): boolean;
  formatStdinPrompt(prompt: string, mode: string): string;
  requiresTty?: boolean;
  readyIndicatorPattern?: RegExp;
  autoRespondRules?: AutoRespondRule[];
  stdinSubmitSequence?: string; // e.g. '\r' for Claude, '\r\n' for Gemini
  probeModels?(): Promise<ProbedModel[] | null>;
}
```

**优化方向**：

```typescript
// packages/shared-types/src/index.ts
export interface AgentAdapter {
  readonly agentType: string;
  readonly requiresTty: boolean;
  readonly stdinSubmitSequence: string;
  readonly readyIndicatorPattern?: RegExp;
  prepare(worktreePath: string, task: string, sessionId: string): Promise<PtyCommand[]>;
  formatPrompt?(task: string): string;
  buildArgs?(opts: { task: string; worktreePath: string }): string[];
}
```

这样新增 Codex、Kimi、OpenCode 时，不需要改 tab 类型，只扩展 adapter 和 harness 配置。

---

### 7. 前端 Store 拆分

**现状问题**：`session-store.ts` 533 行，混合了 sessions、canvasEdges、gitLogs、tabs、UI 状态（settingsOpen、shortcutsHelpOpen）。

**Constellagent 的做法**：单一 Zustand store，但用切片明确分区，并只做 UI 状态；文件树/git 状态通过 IPC 按需拉取。

**优化方向**：

```text
apps/web/src/stores/
├── session-store.ts      # 只保留 sessions 数组与当前选中
├── workspace-store.ts    # workspaces + currentWorkspace
├── tab-store.ts          # tabs + activeTabId
├── ui-store.ts           # settingsOpen / shortcutsHelpOpen / toast
└── connection-store.ts   # WebSocket 连接状态
```

如果业务复杂度继续增长，服务端状态可引入 TanStack Query 做缓存与失效，Zustand 只保留纯 UI 状态。

## 三、代码层面的具体优化建议

### 1. 消除吞异常

**现状**：`WorktreeManager.removeWorktree()` 等多处有 `catch { return [] }` 或 silent swallow，与 `.claude/rules/error-handling.md` 冲突。

**优化**：
- 清理操作失败必须 `fastify.log.warn(error)` 或 `toast.error()`。
- 状态机非法转换继续用 `validateTransition()` 守卫，不要用 try/catch 兜底。

---

### 2. 路径校验强化

**现状**：`assertPathInWorktree()` 用 `startsWith` 字符串匹配，存在路径遍历风险。

**优化**：

```typescript
import { resolve, realpath } from 'node:fs/promises';
import { isSamePath } from './path-utils';

export async function assertPathInWorktree(filePath: string, allowedRoots: string[]) {
  const realFile = await realpath(resolve(filePath));
  for (const root of allowedRoots) {
    const realRoot = await realpath(resolve(root));
    if (realFile === realRoot || realFile.startsWith(realRoot + path.sep)) return;
  }
  throw new Error('Path outside allowed worktree');
}
```

---

### 3. 统一 API 客户端

**现状**：`apps/web/src/lib/api.ts` 只导出 `API_BASE`，大量 `fetch` 重复手写。

**优化**：

```typescript
// apps/web/src/lib/api-client.ts
export const apiClient = {
  async get<T>(path: string): Promise<T> { ... },
  async post<T>(path: string, body: unknown): Promise<T> { ... },
  async patch<T>(path: string, body: unknown): Promise<T> { ... },
  async delete<T>(path: string): Promise<T> { ... },
};
```

统一处理 `response.ok`、JSON 解析、`toast.error()`。

---

### 4. 补齐测试

**现状**：未看到测试目录，核心状态机、Git 操作、diff 解析缺乏自动化覆盖。

**优化**：
- 单元测试：Vitest + `@vitest/ui`，优先覆盖：
  - `validateTransition()` 全状态矩阵
  - `GitDiffParser`
  - `assertPathInWorktree`
- 集成测试：用 `simple-git` 在临时目录创建 repo，测试 worktree 创建/清理。
- E2E：参考 Constellagent 用 Playwright 测试 Electron 桌面端关键路径。

---

### 5. 桌面端状态同步 flush

**Constellagent 的做法**：`beforeunload` 时用 `sendSync` 同步保存状态到主进程。

**优化方向**：在 `apps/desktop/src/preload.ts` 暴露 `api.saveStateSync()`，窗口关闭前同步 flush 本地 UI 状态。

---

### 6. 引入特性开关

**现状**：`CANVAS_ENABLED = false` 硬编码在 `session-store.ts`。

**优化**：移到 `settings-store.ts` 或环境变量，支持运行时切换。

---

## 四、建议的落地优先级

### 第一阶段：结构治理（1-2 周）
1. 拆分 `index.ts` 为 Fastify 插件 + 领域路由
2. 抽离 Repository 层，把 SQL 从 Manager 迁出
3. 拆分前端 store

### 第二阶段：稳定性（2-3 周）
4. Worktree 原子 merge + dry-run
5. 消除吞异常，强化路径校验
6. 终端持久化回放
7. 补齐核心单元测试

### 第三阶段：体验与扩展（3-4 周）
8. WebSocket 二进制帧 + 按 session 订阅
9. Agent Adapter 接口扩展，支持 Codex/Kimi 更深层集成
10. 桌面端状态同步 flush + PR 状态集成（参考 Constellagent）

---

## 五、总体判断

`akari` 的架构意图很清晰：物理隔离（worktree）、状态驱动 UI（WebSocket）、终端即真相（node-pty + xterm）、Agent 抽象（Adapter）。这套方向是对的，比 CLITrigger/Constellagent 的“纯终端复用”多了 HTTP Hook 状态机这一差异化能力。

当前最需要补的不是技术选型，而是**工程纪律**：后端分层、数据访问隔离、测试覆盖、错误处理不吞异常。把这几个做到位，代码基会从一个“能跑的原型”变成“可长期演进的产品”。
