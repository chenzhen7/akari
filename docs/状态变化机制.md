# 状态变化机制

> **更新时间**：2026-06-24
>
> 本文档描述 Akari 当前基于 **HTTP Hook** 的状态流转机制。早期通过终端输出解析 `[CHECKPOINT]` / `[APPROVAL_REQUIRED]` 等魔法字符串驱动状态机的方案已在 Phase 8 中完全废弃。

---

## 状态定义

| 英文值 | 中文含义 |
|--------|----------|
| `initializing` | 初始化中 |
| `idle` | 空闲中（Claude 已启动，等待输入） |
| `running` | 运行中 |
| `waiting` | 待审批 |
| `approved` | 已批准 |
| `paused` | 已暂停 |
| `review` | 审查中 |
| `completed` | 已完成 |
| `failed` | 失败 |
| `merged` | 已合并 |
| `archived` | 已归档 |

---

## 状态转移图

```
初始化中 ──→ 空闲中 ───────────────→ 运行中
    │          │                       │
    │          ├──→ 已暂停 ────────────┤
    │          │         └──────── 待审批
    │          │                       │
    │          ├──→ 失败              ├──→ 已完成 ──→ 已合并
    │          │                       │
    │          └──→ 已归档            └──→ 已归档
    │
    └──→ 失败
```

合法转移表：

| 当前状态 | 可转移到 |
|----------|----------|
| 初始化中 | 空闲中、失败 |
| 空闲中   | 运行中、失败、已归档 |
| 运行中   | 空闲中、待审批、已暂停、已完成、失败、已归档 |
| 待审批   | 运行中、已暂停、失败、已归档 |
| 已批准   | 运行中、已归档 |
| 已暂停   | 运行中、待审批、失败、已归档 |
| 审查中   | 已完成、运行中、已归档 |
| 已完成   | 已合并、已归档、运行中 |
| 失败     | 已归档、运行中 |
| 已合并   | 已归档 |
| 已归档   | 已暂停 |

## 触发路径

### 1. 用户操作 → REST API → WebSocket 广播

```
用户操作（看板拖拽 / 归档 / 恢复）
  → fetch PATCH /sessions/:id/status 或 POST /sessions/:id/archive|restore
  → sessionManager.updateStatus()
      → validateTransition() 校验合法性
      → SQLite 写入新状态 + kanban_column
      → broadcast({ event: 'session:status' })
  → 所有 WebSocket 客户端接收
  → handleServerMessage() → Zustand set → React 重渲染
```

---

### 2. HTTP Hook 事件 → 自动状态变化（核心路径）

Agent 进程运行时，Claude Code 通过 `.claude/settings.local.json` 中配置的 Hook 向 Akari 投递生命周期事件，`hook-dispatcher.ts` 处理后驱动状态机：

| Hook 事件 | 触发时机 | 状态变化 | 其他行为 |
|-----------|----------|----------|----------|
| `SessionStart` | Claude Code 会话启动 | 初始化中 → 空闲中 | — |
| `UserPromptSubmit` | 用户提交提示 | 已暂停 / 待审批 / 空闲中 → 运行中 | — |
| `PermissionRequest` | Claude 请求权限 | **无状态变化** | 仅记录审批日志 |
| `Stop` | 当前轮次回复结束 | 运行中 / 待审批 → 空闲中 | 提取 `last_assistant_message`，广播 `session:lastMessage` |
| `StopFailure` | API 报错 / token 超限 | 运行中 / 已暂停 / 待审批 → 失败 | 终端显示红色错误行 |

完整链路：
```
Claude Code 触发 Hook
  → HTTP POST /sessions/:id/hooks
  → HookDispatcher.dispatchHookEvent()
  → sessionManager.updateStatus() / setLastAiMessage()
  → SQLite 更新
  → broadcast(session:status / session:lastMessage) → WebSocket → 前端 Zustand → UI
```

> **注意**：`PermissionRequest` 当前仅做日志记录，**不挂起 HTTP 请求**，也不修改会话状态。Claude Code 仍使用原生权限确认流程。

---

### 3. 会话创建时的自动流转

```
POST /sessions
  → createSession()
      → 写入 SQLite，状态：初始化中
      → broadcast(session:created) → 前端新增卡片
  → initSession() 异步执行
      → createWorktree()（创建 Git Worktree 与分支）
      → createTerminal()（node-pty 启动 Shell）
      → agentAdapter.prepare()（写入 .claude/settings.local.json）
      → updateStatus('idle')  ← 自动变为「空闲中」
      → 若任何步骤抛出异常 → updateStatus('failed')
```

---

### 4. 终端退出

```
node-pty 进程退出
  → terminal-mux.ts 发射 terminal:exit { sessionId, terminalId, exitCode }
  → SessionManager.wireEvents() 响应
  → 若该会话已无其他终端：
       exitCode === 0 → completed
       exitCode !== 0 → failed
  → broadcast(session:status) → 前端更新
```

---

### 5. 归档与恢复

```
用户归档
  → POST /sessions/:id/archive
  → archiveSession()
      → kill 该会话所有 terminal
      → updateStatus('archived')

用户恢复
  → POST /sessions/:id/restore
  → restoreSession()
      → updateStatus('paused')
```

---

### 6. WebSocket 连接时全量同步

```
新客户端连接 /ws
  → 立即推送 workspace:list、sessions:list、canvas:edges
  → 当客户端订阅某个 workspace 后，推送 workspace:activated（该 workspace 被显式激活）
  → 推送所有 active 会话的当前 diff
  → 前端 handleServerMessage('sessions:list') → 覆盖 Zustand sessions
```

## 看板列与状态的映射

| 看板列 | 对应状态 |
|--------|----------|
| 待办（backlog） | 初始化中、空闲中 |
| 进行中（in-progress） | 运行中、已暂停 |
| 待审批（waiting-review） | 待审批、审查中 |
| 已批准（approved） | 已批准 |
| 完成（done） | 已完成、失败、已合并、已归档 |

用户拖动看板卡片时，前端同时调用 `PATCH /sessions/:id/status` 将状态同步到后端。

## 触发源汇总

| 触发源 | 处理位置 | 状态变化 |
|--------|----------|----------|
| 会话初始化成功 | `initSession()` | 初始化中 → 空闲中 |
| 会话初始化失败 | `initSession()` catch | 初始化中 → 失败 |
| `SessionStart` Hook | `hook-dispatcher.ts` | 初始化中 → 空闲中 |
| `UserPromptSubmit` Hook | `hook-dispatcher.ts` | 已暂停 / 待审批 / 空闲中 → 运行中 |
| `PermissionRequest` Hook | `hook-dispatcher.ts` | 无（仅日志） |
| `Stop` Hook | `hook-dispatcher.ts` | 运行中 / 待审批 → 空闲中 |
| `StopFailure` Hook | `hook-dispatcher.ts` | 运行中 / 已暂停 / 待审批 → 失败 |
| Agent 进程正常退出（exit 0） | `terminal:exit` 处理器 | 运行中 / 已暂停 → 已完成 |
| Agent 进程异常退出（exit ≠ 0） | `terminal:exit` 处理器 | 运行中 / 已暂停 → 失败 |
| 用户拖看板 | REST `PATCH /status` | 按看板列映射 |
| 用户归档 | REST `POST /archive` | 当前状态 → 已归档 |
| 用户恢复 | REST `POST /restore` | 已归档 → 已暂停 |

## 与旧机制的区别

| 旧机制（已废弃） | 新机制 |
|-----------------|--------|
| 终端输出解析 `[CHECKPOINT]` / `[APPROVAL_REQUIRED]` 魔法字符串 | Claude Code HTTP Hook 投递结构化事件 |
| `TerminalMultiplexer.detectMarkers()` 驱动状态 | `HookDispatcher.dispatchHookEvent()` 驱动状态 |
| Checkpoint 进度更新依赖终端输出 | 通过 `Stop` Hook 的 `last_assistant_message` 更新 |
| 审批通过 `y\n` / 拒绝 `n\n` 写入终端 | `PermissionRequest` 当前不阻塞，由 Claude Code 原生处理 |

详情见 [docs/开发计划/phase-8-基于Hooks的Agent状态流程机制改造计划.md](docs/开发计划/phase-8-基于Hooks的Agent状态流程机制改造计划.md)。

## 测试占位区（临时内容）

> 以下内容为测试占位，仅供验证文档编辑 / diff / 提交流程使用，可随时删除。

### 状态流转快速自查

- 初始化成功后，会话应从 `initializing` 自动进入 `idle`，无需人工干预。
- `Stop` Hook 后若 `last_assistant_message` 为空，前端应显示「本轮无输出」而非空白。
- 待审批状态下 `UserPromptSubmit` 到达时，应回到 `running` 并继续执行。
- 已归档会话再次 `StopFailure`，应被 `validateTransition()` 拒绝并记录 warn 日志。
