# 隔离法调试

## 核心原则

“由简入奢易，由奢入简难。” 当面对错综复杂的系统现象时，盲目修改和猜测往往会陷入“拆东墙补西墙”的陷阱。隔离法要求我们退回到绝对安全的最小可行状态，以此为基准，采用单变量叠加（Single Variable Increment）的方式，精确捕捉系统行为发生质变的临界点。

## 分步工作流程

### 第一步：定义问题边界

在开始剥离之前，先明确以下内容：
- **观察到的失败**是什么？
- **预期行为**是什么？
- 在什么样的**最小上下文**中会出现失败？
- 当前涉及哪些组件、层级或因素？

### 第二步：剥离到最小工作模型

创建最简单的、应该能正常工作的版本：

**代码层面：**
- 移除与失败功能无关的所有业务逻辑
- 将真实依赖替换为硬编码值、存根或 null
- 移除所有配置，使用默认值
- 只保留绝对最小的代码路径

**环境层面：**
- 尽可能使用全新/干净的环境
- 禁用缓存、拦截器、中间件和过滤器
- 使用最小化的配置文件

**验证：** 确认最小模型按预期工作。

### 第三步：逐步还原

按照从“最不可能”到“最可能”的顺序，每次只还原一个因素。每一步都需要交由用户进行实际测试。

1. **还原一个被移除的因素**
2. **运行测试 / 验证行为**
3. **如果仍然正常 →** 该因素不是原因，记录下来继续
4. **如果出现问题 →** 找到了罪魁祸首，停下来深入排查该因素
5. **如果不确定 →** 独立测试该因素以进一步隔离

互动执行规范：

1. 单变量恢复： 仅加回一个被移除的因素（如：加回某个配置项，或启用某个拦截器）。

2. 交出控制权： 提供明确的修改指示，请用户在当前环境下运行测试。

3. 根据用户反馈分支：

    - 如果用户反馈【仍正常】： 说明该因素是安全的。在记录表中标记为 Pass，保持当前状态（或回滚至基准），准备提供下一个因子的还原指令。

    - 如果用户反馈【出现问题】： 成功定罪！该因子即为触发 Bug 的临界变量。立即停止其余因素的还原，直接进入第四步。


### 第四步：深入排查罪魁祸首

一旦确认导致问题的因素：
- 独立检查它的实现
- 检查它与其他组件的交互
- 验证它的输入和输出
- 查阅文档了解已知问题
- 搜索类似的 bug 报告或堆栈跟踪

### 第五步：验证修复

- 修复根因
- 在最小模型中测试修复
- 还原所有剩余因素
- 验证完整场景是否正常工作

## 沟通模板

向用户汇报进度时使用以下格式：

```
隔离调试进度：
- 基础模型（已剥离）：[正常 / 失败]

验证历史记录：
- 因子 1：[描述] → 用户验证：[正常] (已排除)
- 因子 2：[描述] → 用户验证：[正常] (已排除)

当前测试轮次：
- 待还原验证因子：[描述]
👉【请用户操作】：请在加回上述因子后运行测试，并反馈 [正常 / 失败]。
--------------------------------------------------
- 确认罪魁祸首：[当用户反馈失败时填入]
- 根因分析：[解释为什么该因子会导致整体崩溃]
```

## 示例

### 示例 1：API 接口报错

**问题：** POST `/api/order` 返回 500，但错误信息被吞掉了。

**剥离过程：**
1. 新建一个只返回 `"ok"` 的 `/api/test` 接口 → 验证正常
2. 加回请求体解析，返回硬编码响应 → 验证正常
3. 加回数据库调用，使用硬编码查询 → 验证正常
4. 一行一行加回实际业务逻辑 → 找到报错的那一行

### 示例 2：前端组件无法渲染

**问题：** 一个 React/Vue 组件在加载时崩溃。

**剥离过程：**
1. 组件中只渲染 `<div>test</div>` → 验证正常
2. 逐个加回 props，使用硬编码值 → 找到是否是某个 prop 导致的
3. 逐个加回子组件 → 找到是否是某个子组件导致的
4. 逐个加回 hooks/effects → 找到是否是生命周期逻辑导致的
5. 加回实际数据获取 → 找到是否是数据格式导致的

避免的反模式
- 禁止跳过最小模型： 凭直觉去猜测该先测哪个因素，往往会浪费大量时间。

- 禁止单轮复合还原： 绝不要在一次验证中同时加回两个或多个因素。一旦报错，将无法分清是谁引发的。

- 禁止主观假设： 绝不要说“不可能是这个组件的问题”。在隔离法中，只有“用户实测通过”的组件才是安全的。

- 禁止浮于表面： 找到报错因子后，必须阐明其背后的底层机理，而不是通过临时 Wrap 一个 try-catch 来掩盖症状。

## 记住

- 目标是**确定性**，不是速度。每步都在消除不确定性。
- 如果最小模型也失败，说明问题比想象的更根本。
- 记录每一步，方便用户理解推理过程。
